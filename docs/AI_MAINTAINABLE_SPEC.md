# Get Yourself 重构规范 —— 将老项目重构为 AI 可维护项目

> 依据：《从胡言乱语到精准改代码：我是如何让 AI 读懂老项目的》
> 目标：让 AI（及新同学）无需反复询问，即可高效定位问题、给出贴合项目的方案。
> 原则：**同样的事情，只需要跟 AI 强调一遍即可。**

---

## 0. 总纲：文章五步 → 本项目五阶段

| 文章方法论 | 本项目落地阶段 | 核心交付物 |
|---|---|---|
| ① AI 上下文工程（从 AGENTS.md 开始） | **阶段 A：知识底座** | 根 `AGENTS.md` + 模块级 `AGENTS.md` + 知识索引 |
| ② 移除不再起作用的代码 | **阶段 B：清死代码** | 死代码清单 + 清理 MR |
| ③ 做减法，复杂架构简单化 | **阶段 C：架构收敛** | 简化方案 + 落地 |
| ④ 定规范，给项目设置约束边界 | **阶段 D：规范约束** | 本 Spec 落地为代码结构标准 |
| ⑤ 定标准，建设自动化测试工程 | **阶段 E：质量护栏** | 单测 / E2E / 视觉回归 / MR 流水线 |
| ⑥ 将债务治理常态化 | **阶段 F：长效机制** | 问题日志流转 + 日常治理节奏 |

**执行方式：每个阶段有独立 MR，可独立验收、独立回滚。禁止一个阶段没验收就开下一个。**

## 1. 阶段 A：AI 上下文工程（知识底座）

### 1.1 根目录 `AGENTS.md` —— 只做索引，不做细节

根 `AGENTS.md` 的结构（模板）：

```markdown
# Get Yourself

面向大学生的个人成长记录与能力发展平台（Spring Boot 3.3 + Vue 3 + TS 前后端分离）。

## 知识索引

| 领域 | 位置 | 摘要 |
|---|---|---|
| 系统架构总览 | `README.md` | 模块清单、技术栈、部署方式 |
| 能力评分系统 | `docs/Java确定性能力评分引擎_v2.md` 等 | 四层流水线：证据抽取→Java 评分→Judge→HAC 聚类 |
| 检索推荐链路 | `backend/src/.../retrieval/` + `docs/RAG召回评测集_30条_v1.md` | BM25 + Embedding 混合召回 |
| 问题日志（已解决） | `backend/PROBLEM_LOG.md` | 历史问题的原因与解法，AI 排障先查这里 |
| 待处理问题 | `docs/待处理问题.md` | 未定稿方向，AI 方案设计前先看 |
| 优化 backlog | `backend/AGENT_OPTIMIZATION_BACKLOG.md` | AI/Agent 优化项 |

## 项目规范（强制）

- 本仓库规范以 `docs/AI_MAINTAINABLE_SPEC.md` 为准。
- AI 代提交代码时，commit message 必须带清晰类型前缀（`feat:` / `fix:` / `refactor:` / `docs:` / `test:`），单行 ≤ 72 字符。
- 模块级知识就近落盘到对应模块的 `AGENTS.md`，并同步更新本文件索引。

## 知识落盘规范

- 根 `AGENTS.md` 只保留「路径 + 1~2 句摘要」，细节放模块级文档。
- 对话中出现可复用的规则 / 兼容性 / 排障结论时，必须就近落盘，避免下次重新摸索。
- 发现索引过期或不准确时，主动修改。
```

### 1.2 模块级 `AGENTS.md` —— 知识就近落盘

- **后端**：每个业务模块目录（如 `abilityscore/`、`retrieval/`、`coach/`）放一个 `AGENTS.md`，记录：该模块的职责边界、关键类地图（Controller/Service/Entity/Repository 各是哪个）、与其他模块的依赖关系、已踩过的坑。
- **前端**：`src/api/`、`src/stores/`、`src/views/` 各自一个 `AGENTS.md`，记录 API 约定、状态管理边界、页面职责。
- **只写 AI 查不到或查起来很贵的信息**（运行链路、历史决策、兼容性约束、未跑通的尝试），不写代码本身能看出来的事。

### 1.3 知识更新流程

```
对话中出现新知识 → 判断归属模块 → 写入模块 AGENTS.md → 更新根 AGENTS.md 索引
排障结论 → 写入 backend/PROBLEM_LOG.md（按 001 模板：发生了什么/原因/解决方式/结果）
待定方向 → 写入 docs/待处理问题.md（落地后迁移到 PROBLEM_LOG.md）
```

## 2. 阶段 B：清死代码

### 2.1 已发现的死代码（立即可清）

| 文件 | 证据 | 处理 |
|---|---|---|
| `frontend/legacy-index.html` (36KB) | 仅被自身引用的旧页面，真实 `index.html` 只加载 `/src/main.ts` | 删除（先确认无人工直接访问） |
| `frontend/app.js` (152KB) | 仅被 `legacy-index.html` 引用 | 删除 |
| `frontend/styles.css` (48KB) | 仅被 `legacy-index.html` 引用 | 删除 |

### 2.2 系统性清理方法

1. **引用分析**：用 IDE / grep 找完全无引用的类、方法、文件；注意「互相引用但都不被入口引用」的死岛（如上三件套）。
2. **环境分支排查**：`grep -rn "环境判断\|if (.*env" src` 找复制粘贴遗留的客户端兼容分支；对照 `.env.example` / `railway.toml` 确认哪些环境变量真实存在。
3. **链路验证**：对「有引用但不确定是否运行」的代码，先加日志/断点跑真实场景确认，再删除——**不能只靠静态引用判断**（文章的教训）。
4. **删除纪律**：每次删除一个独立主题，跑通测试 + 本地全链路验证后再提交，禁止大爆炸式删除。
5. **沉淀**：删除结论写进模块 `AGENTS.md`（"XX 已下线，勿再引用"），防止 AI 下次又把它建回来。

### 2.3 清理验收标准

- [ ] 死代码清单全部处理（删除 or 标注"保留原因"）
- [ ] `mvn test` 全绿 + 前端 `npm run build` 通过
- [ ] 核心链路（登录→成长时间线→AI 教练→能力评估）手工回归一次
- [ ] 清理结论已落盘到 AGENTS.md

## 3. 阶段 C：架构收敛（做减法）

### 3.1 复杂度体检清单

| 检查项 | 本项目现状 | 判断标准 |
|---|---|---|
| 消息队列 | RabbitMQ + Outbox Pattern | 是否所有 MQ 场景真的需要最终一致性？低频场景可否改同步调用？ |
| 检索链路 | BM25 + Embedding + Rerank + 本地打分 | `docs/待处理问题.md` 已列优化方向，评估打分权重复杂度 |
| 缓存 | Redis 会话 + 7 天 TTL | 是否有过期缓存无人清理？ |
| Agent 模块 | Run/Step/Artifact 全链路追踪 | 追踪粒度是否过细？ |
| 前端状态 | 仅 auth 一个 store | ✅ 良好，保持克制 |

### 3.2 简化原则（写进 AGENTS.md 的决策依据）

1. **架构的价值是把复杂度压下来，不是看起来高级。**
2. **好的架构立足于现在，随业务变动调整，不为"想象中的未来"设计。**
3. 每次重构只解决一个复杂度问题；重构要彻底，**不允许留一半**（文章最大的教训：不彻底的重构产生新债务）。
4. 重构前先评估：这个复杂度现在有人用吗？可见未来会用吗？——两个"否"就砍。

### 3.3 简化验收标准

- [ ] 每个被简化的链路有"简化前 vs 简化后"对比记录（写入 AGENTS.md）
- [ ] 下线功能无用户反馈异常（观察 1 个发布周期）
- [ ] 模块间依赖图比简化前更小（用 `jdeps` 或人工梳理确认）

## 4. 阶段 D：规范约束（标准实现逻辑）

### 4.1 后端模块标准结构（新模块模板）

```text
backend/src/main/java/com/getyourself/backend/<module>/
├── <Module>Controller.java     # 只做参数校验 + 调 Service + 返回 DTO，不写业务逻辑
├── <Module>Service.java        # 业务逻辑唯一住所，禁止 Controller 里写业务
├── <Module>Entity.java         # JPA 实体，字段与表一一对应
├── <Module>Repository.java     # 只声明查询方法，复杂查询进 Service 或 Specification
├── <Module>Dtos.java           # 请求/响应 DTO 聚合文件
└── <Module>AGENTS.md           # 模块知识：职责边界 + 关键类地图 + 依赖 + 坑
```

**已遵循良好实践（保持）：** `auth/` 模块的 `Controller / Dtos / Service / Entity / Repository / Role` 分层清晰；`common/` 已有 `ApiException`、`GlobalExceptionHandler`、`PageResponse`、`CurrentUser`。

**强制约定：**
- 异常：业务错误一律抛 `ApiException`，由 `GlobalExceptionHandler` 统一转 JSON；禁止 Controller 里 try-catch 吞异常。
- 分页：统一返回 `PageResponse<T>`。
- 当前用户：从 `CurrentUser` 取，禁止 Controller 直接解析 Token。
- 跨模块调用：只允许 Controller→Service 或 Service→Repository 单向依赖；Service 之间禁止循环依赖。
- 新增表：一律 Flyway 迁移脚本（`V<版本号>__<描述>.sql`），禁止 `ddl-auto: update` 直改。

### 4.2 前端模块标准

| 目录 | 职责 | 禁止 |
|---|---|---|
| `src/api/` | 每个后端领域一个文件，统一走 `client.ts` 的 `api.get/post/put/delete` | 组件里直接 `fetch`；重复封装 |
| `src/stores/` | Pinia 全局状态（目前仅 auth，新增需论证必要性） | 页面局部状态放 store |
| `src/views/` | 页面级组件，一个路由一个 view | 跨页面复制大段逻辑 |
| `src/components/` | 可复用组件，命名与设计稿规范一致 | 为单个页面造"通用"组件 |
| `src/router/` | 路由 + 鉴权守卫 | 在组件内写路由跳转逻辑绕过守卫 |

**前端约定：**
- API 错误统一走 `client.ts` 的 `ApiError`，401 已自动登出（`AUTH_UNAUTHORIZED_EVENT`），页面不得重复处理 401。
- 请求 DTO 类型放 `src/types/`，与后端 DTO 字段一一对应。

### 4.3 规范验收标准

- [ ] 新代码符合 4.1 / 4.2 模板（由 AI 评审规则检测）
- [ ] 存量代码逐步迁移，迁移一个模块验收一个模块

## 5. 阶段 E：自动化测试工程

### 5.1 单测标准（Mock 数据）

- 覆盖：能力评分引擎（已有 8 个测试 ✅）、检索打分、鉴权、业务 Service 的核心分支。
- 原则：**确定性逻辑必须测**（计算、判断、边界），纯胶水代码不测。
- 用 `spring-boot-starter-test` + Mockito，跑 `mvn test`。

### 5.2 E2E 标准（Playwright，待建设）

- 覆盖多页面链路：登录 → 成长时间线 → 写日记 → AI 教练对话 → 能力评估查看 → 挑战完成。
- 真实环境跑，需要测试账号 + 测试数据治理（测试产生的脏数据定期清理，防止账号触上限——文章的教训）。
- 用 P0/P1/P2 分级：P0 核心链路必测，P1 主要功能，P2 次要。

### 5.3 视觉回归标准（待建设）

- 大截图测布局异常（像素偏差阈值放宽）；组件级小用例测细节样式（阈值严格）。
- 视觉产物跟代码仓库走；流水线失败时 MR 上肉眼可见（防止 AI 为了过流水线偷偷改样式）。

### 5.4 MR 流水线（目标形态）

```
提交 → 单测 → E2E → 视觉回归 → AI 评审（规范合规检测）→ 人工 review → 合入
```

- AI 评审规则：检测 4.1 / 4.2 规范遵守情况（是否 Controller 写业务、是否绕过 client.ts、是否新增表没走 Flyway 等）。
- 每期迭代一个能力（参考文章：第一期搭能力、第二期接流水线、第三期补用例、第四期补复杂链路）。

## 6. 阶段 F：债务治理常态化

1. **问题日志流转闭环**：`docs/待处理问题.md`（未定稿）→ 落地后迁移到 `backend/PROBLEM_LOG.md`（已解决，含原因与解法）。
2. **日常顺手治理**：开发/AI 迭代新功能时，遇到历史不规范代码顺手按新规范重构（小步提交），不攒大专项。
3. **AI 评审兜底**：MR 时 AI 检查是否新增了规范违规，把"依赖人自觉"变成"机制强制"。
4. **定期复盘**：每季度过一遍 `待处理问题.md`，确认方向是否仍有效，避免"起了头没下文"的债务。

## 7. 分步执行路线图（Roadmap）

| 步骤 | 内容 | 预计工作量 | 交付物 |
|---|---|---|---|
| **Step 0** | 建根 `AGENTS.md` + 知识索引（含本文档链接） | 0.5 天 | `AGENTS.md` |
| **Step 1** | 清死代码（legacy 三件套 + 引用扫描 + 环境分支排查） | 1~2 天 | 清理 MR + 死代码结论落盘 |
| **Step 2** | 复杂度体检，选出 1 个可砍的复杂度（如 MQ/检索链路） | 1~2 天 | 简化方案 + 落地 MR |
| **Step 3** | 写核心模块 `AGENTS.md`（abilityscore / retrieval / coach / auth 优先） | 1~2 天 | 模块知识底座 |
| **Step 4** | 单测补强（核心链路确定性逻辑） | 2~3 天 | 测试用例 + 覆盖率报告 |
| **Step 5** | E2E 框架搭建 + P0 链路用例 | 3~5 天 | Playwright 用例 + 流水线 |
| **Step 6** | 视觉回归 + MR 流水线 + AI 评审规则 | 3~5 天 | 流水线 + 评审规则文件 |
| **Step 7** | 常态化：问题日志流转 + 每季度复盘节奏 | 持续 | 治理机制文档 |

> 每步独立 MR、独立验收；**不跳步，不并行**。Step 0~1 是地基，先把 AI 的"眼睛"和代码的"干净度"搞定，后面的自动化才有意义。
