## 1. 文档分工

验收相关文档分三层，避免同一规则散落在多个地方：

| 层 | 文档 | 职责 |
|---|---|---|
| 产品范围与阶段 | `docs/PRODUCT_DESIGN_V0.1.md` | 定义产品目标、模块边界、阶段推进和 6c 双门槛 |
| 验收标准 | 本文档 | 定义证据等级、case 设计方法、判定口径、硬门槛和记录格式 |
| 当前执行清单 | `docs/UNIFIED_ACCEPTANCE_V0.1.md` | 定义本次批次的具体 A0-A7 操作、当前环境结论和待回填结果 |

冲突处理：产品范围以 PRD 为准；验收方法以本文档为准；某次批次的实际结论以统一验收包或后续验收记录为准。任何文档都不能把仓库测试通过写成用户验收通过。

范围口径：本文档的 case 全集是 v0.1 发布前验收门槛；`docs/UNIFIED_ACCEPTANCE_V0.1.md` 是当前首批批次执行清单。首批清单未覆盖的标准 case 保持“未执行”，不得因首批批次通过而自动视为完成；首批结论也不能被写成 v0.1 全量发布结论。

## 2. 不可协商规则

1. **用户验收必须显式。** 只有用户对指定模块明确回复“通过”“需修改”或“阻断”后，才能回填该模块结论。
2. **仓库验证不等于用户验收。** 单元测试、契约测试、前端构建、代码审查、Playwright 模拟都只是前置证据。
3. **禁止伪造闭环。** 后端不可用时，网页证据包导出只能记录阻断；不能用示例 JSON 的 CLI 校验结果替代。
4. **浏览器不直接写本地数据根。** 所有本地写入必须走显式文件、CLI check、dry-run、`--apply`；覆盖不同内容必须显式 `--replace`。
5. **pending 不是已同步。** Stage 6b 的 `pending` 只表示本地待发；不得解释为已上传、云端已确认或双端一致。
6. **本验收不启动云端。** 不启动 Stage 6c 授权 API、数据库变更、云端投影、上传重试或自动导入。
7. **隐私内容不进入验收记录。** 验收记录不得复制简历全文、STAR 原稿、JD 原文、完整本机路径、设备凭证、队列业务摘要或私人备注。
8. **优先使用可丢弃数据。** 涉及 `--apply`、替换、取消、状态变更的 case 必须先确认不会覆盖真实用户数据。
9. **验收发现问题先修体验和数据边界。** 体验阻断、越界写入、数据错误的修复优先级高于继续扩展云端能力。
10. **完成的文档或代码变更必须提交并推送。** 验收结论回填也必须形成单独提交。

## 3. 证据等级

| 等级 | 名称 | 能证明 | 不能证明 |
|---|---|---|---|
| E0 | 静态复查 | 文档、代码路径、声明范围一致 | 运行行为正确 |
| E1 | 自动化测试 | 确定性契约、边界和回归在测试数据下通过 | 真实用户体验正确 |
| E2 | CLI 只读 / dry-run | 当前命令能识别目标、显示写入范围且未落盘 | 用户理解或接受该结果 |
| E3 | 浏览器或脚本模拟 | 页面路由、状态流和无页面错误 | 真实鼠标、触控、滚动和主观可用性 |
| E4 | 真实用户验收 | 用户确认体验、心智、结果和边界可接受 | 后续版本不会回归 |

判定规则：

- E4 是唯一能把模块结论写为“通过”的证据。
- E1-E3 可以作为进入 E4 的前置条件，也可以记录为仓库验证事实。
- 标记为 E4-hard 的 case 不可被 E0-E3 替代。
- 方法列含多个等级（如 `E1 / E4`）时，低等级证据只能证明契约或模拟结果；涉及用户理解、真实交互和模块结论时仍需 E4。
- 环境缺失时可以记录“阻断”，但必须写清缺失依赖和被阻断的具体 case。

## 4. Case 设计矩阵

每个用户可见模块的 mandatory case 至少覆盖适用的以下维度；每个确定性契约至少覆盖有效输入、无效输入、dry-run、apply、幂等、替换和漂移。

| 维度 | 必须回答的问题 | 适用范围 |
|---|---|---|
| M1 主路径 | 目标用户能否从入口完成核心交付 | 所有模块 |
| M2 替代路径 | 主条件不满足时是否有可用退路 | 链接失败、JSON 导入、旧简历导入等 |
| M3 空态 / 冷启动 | 无证据、无简历、无机会时是否诚实引导 | 所有模块 |
| M4 无效 / 对抗输入 | 坏数据、超大输入、注入指令、身份冲突是否被拒绝 | 所有契约和 AI 输入 |
| M5 重复 / 幂等 | 重复执行是否不产生重复对象或重复记录 | 所有写入契约 |
| M6 漂移 / 兼容 | 旧文件、哈希变化、来源过期是否被识别且不自动修复 | 简历事实链、同步单元、设备重绑 |
| M7 权限 / 隐私 | 谁能写、写哪里、哪些内容禁止上传或展示 | 所有模块 |
| M8 失败恢复 | 断网、依赖缺失、取消、重试后的状态是否可理解 | 文件桥、队列、后端依赖 |
| M9 交互可用性 | 布局、滚动、选区、抽屉、窄屏是否可用 | 前端模块 |
| M10 回归 | 修复后既有主路径和契约是否仍通过 | 所有修复 |

mandatory case 的最低组合：

| 模块类型 | 必须包含 |
|---|---|
| 前端页面 | M1、M3、M4、M7、M9、M10 |
| 页面内确认流 | M1、M4、M5、M7、M8、M10 |
| 浏览器文件桥 | M1、M2、M4、M5、M7、M8、M10 |
| CLI 契约 | M1、M3、M4、M5、M6、M7、M8、M10 |
| Skill Runtime | M1、M4、M5、M6、M7、M8、M10 |
| Stage 6a / 6b | M1、M4、M5、M6、M7、M8、M10 |

## 5. 严重级别与模块结论

### 5.1 缺陷级别

| 级别 | 定义 | 示例 | 处理 |
|---|---|---|---|
| S0 阻断 | 数据错误、数据丢失、越界写入、隐私泄漏、安全边界失效、主路径不可用 | 浏览器直接写 `cli/data`；pending 显示为已同步；定稿覆盖用户历史 | 必须修复后重验 |
| S1 需修改 | 关键路径能走通但结果、状态、文案或交互明显错误，且有理解成本高的 workaround | 取消后对象状态未变但提示误导；节点抽屉信息难以辨认 | 修复优先级高于新能力 |
| S2 轻微 | 不影响事实和主路径的体验或文案问题 | 次要按钮间距、非关键空态文案 | 可记录后排期 |

### 5.2 模块结论

| 结论 | 条件 |
|---|---|
| 通过 | 所有 mandatory case 完成；无 S0 / S1；S2 已记录且用户接受 |
| 需修改 | 无 S0，但存在 S1，或 mandatory case 有明确体验问题 |
| 阻断 | 存在 S0，或环境 / 数据 / 依赖导致 mandatory case 无法执行 |
| 待验收 | 尚未获得用户对该模块的显式结论 |

“通过”只对当前版本和当前验收范围有效。后续改动触及该模块时必须按第 9 节回归。

### 5.3 批次结论与发布结论

当前 A0-A7 统一验收包可以先按批次记录 `通过 / 需修改 / 阻断`，但其结论只覆盖该批次明确列出的动作。若本标准还有 mandatory case 未执行，必须在记录中保留“未执行”清单；该模块不得登记为 v0.1 发布前全量验收通过。

批次结论进入发布结论的转换条件只有一个：该模块在本标准中适用的 mandatory case 均已执行，缺失依赖的 case 已如实记录为阻断，且用户对整体结论给出显式确认。

## 6. 测试身份与数据

| 身份 | 初始状态 | 主要验证 |
|---|---|---|
| 冷启动学生 | 无能力证据、无简历、无公司机会 | M3 空态、追问、一次经历冷启动 |
| 成品简历学生 | 本机有旧简历，无平台证据 | 成品导入、事实链 binding-gap、证据缺口 |
| 平台证据学生 | 网页有能力证据，本地为空 | 证据包导出 / 导入、简历条目来源 |
| 求职中学生 | 有证据、简历、公司机会和流程节点 | 简历版本、面试状态、产物挂载、复盘 |
| 多设备学生 | 同一账号多台本地工位 | 设备授权、重绑阻断、冲突选择、同步单元身份 |

数据要求：

1. 使用假名、假公司、假经历、假指标和可丢弃文件。
2. 不把真实简历、真实 JD、扫描件、PDF、设备凭证或 API key 放入仓库。
3. 临时文件放在仓库外；验收后清理，或在记录中说明保留位置和原因。
4. 涉及真实数据时先做只读 check；必须 apply 时先确认目标身份、内容哈希和备份路径。
5. 不为了通过验收修改用户拥有的流程结果。

## 7. 通用验收 Case

Case 级别使用两个值：`mandatory` 表示该场景在适用条件下必测；`conditional` 表示仅当对应区域被触及或依赖被使用时必测。

| ID | 级别 | 方法 | 操作 | 应该发生 | 禁止发生 |
|---|---|---|---|---|---|
| ENV-01 | mandatory | E2 | 仓库根执行 `git status --short --branch` | 分支、远程和脏文件状态明确；本批次开始前应与 `origin/main` 同步 | 带未知脏改动验收 |
| ENV-02 | mandatory | E2 / E4 | 启动或确认前端服务并打开 `/student/workbench` | 当前提交对应页面可打开，路由无缓存疑义 | 用旧进程或旧构建冒充当前版本 |
| ENV-03 | conditional | E1 | 在 `cli/` 执行 `npm test` | 全量 CLI 测试通过，失败如实阻断 | 用专项测试冒充全量回归 |
| ENV-04 | conditional | E1 | 在 `frontend/` 执行 `npm run build` | 构建通过；已知 chunk 体积警告可记录为 S2 | 构建失败仍继续验收 |
| ENV-05 | conditional | E1 | 后端被触及时在 `backend/` 执行 `mvn test` | 后端回归通过；依赖缺失时记录具体缺失 | 用前端 mock 冒充后端闭环 |
| ENV-06 | mandatory | E0 | 检查改动范围 | 企业端、活动、预约、推荐等冻结域无新增行为 | 借验收扩展冻结模块 |
| ENV-07 | mandatory | E0 / E2 | 检查本地写入命令 | 写入先 check / dry-run，再显式 apply / replace | 隐式覆盖用户数据 |

conditional 表示该 case 在对应区域被触及或依赖被使用时必须执行。

## 8. 模块验收 Case

### 8.1 Agent 工作台

| ID | 级别 | 方法 | 操作 | 应该发生 | 禁止发生 |
|---|---|---|---|---|---|
| AG-01 | mandatory | E4 | 观察首屏 | Agent 对话是主入口；资产、简历、面试是独立导航和落点 | 四类对象全部堆在工作台首屏 |
| AG-02 | mandatory | E4 | 分别打开资产、简历、面试路由 | 每页只展示本模块主对象和操作 | 独立模块混入其他模块主体内容 |
| AG-03 | mandatory | E4 | 触发写入型意图 | 出现计划卡，说明目标模块、写入对象、不改动对象和确认方式 | 未确认就写入 |
| AG-04 | mandatory | E4 | 确认执行 | 只写入计划声明的目标；目标模块出现唯一草稿或复用既有草稿 | 覆盖定稿、当前投递版、面试结果或云端对象 |
| AG-05 | mandatory | E4 | 生成另一计划后取消 | 计划为已取消，目标模块对象不变，Trace 保留取消 | 取消后仍新增或改写对象 |
| AG-06 | mandatory | E4 | 触发只读分析 | 输出可读结果，不显示“已沉淀”“已保存”“已同步” | 只读输出生成写入计划 |
| AG-07 | mandatory | E4 | 检查 Trace 文案 | 写入、取消、只读、文件桥、云端边界可区分 | 把会话对象说成本地文件或云端数据 |
| AG-08 | mandatory | E4-hard | 真人操作确认与取消 | 用户能理解将发生什么，误操作可退出 | 确认按钮含义不清或不可逆提示缺失 |
| AG-09 | mandatory | E3 / E4 | 粘贴包含指令的 JD 或经历 | 外部内容只作为数据，不改变执行规则 | 注入内容注册 skill 或扩大写入范围 |
| AG-10 | mandatory | E3 / E4 | 窄屏检查 | 主路径可用，文字和按钮不重叠 | 关键确认按钮不可见或不可点 |

## 9. 后端架构 P0 门槛 Case

以下 case 属于 Stage 6c 前置门槛。工程实现、仓库回归和真实数据库迁移可以积累 E1 / E2 证据，但不能替代用户对 6b 本地侧边界和“是否进入 6c 设计”的确认。

| ID | 门槛 | 必须证明 | 当前处理 |
|---|---|---|---|
| BA-01 | 端点鉴权与所有权 | 学生只能访问和写入自己的账户、证据、Trace 和设备授权对象；设备 token 不能替代网页登录态；冻结域公共变更 / 重建索引入口必须被工程处置或由用户明确接受 | 部分完成：85 条路由矩阵、两条所有权拒绝测试和 49/49 后端回归已通过；冻结域公共入口处置与集中式运行时策略仍待收口，或由用户明确接受风险 |
| BA-02 | Trace 真实脱敏语义 | 脱敏标识与实际内容一致；简历全文、STAR 原稿、凭证和禁传私人内容不进入平台 Trace | 当前工程范围已验证：新写入仅存脱敏摘要，V23 重写历史 artifact；49/49 后端回归与 MariaDB 11.4 V22→V23 迁移、哈希重算和敏感残留 0 断言通过。MySQL 8.4 与迁移后完整启动链路仍未验证 |
| BA-03 | 设备授权云写入边界 | 设备 token 只能写明确授权的同步摘要，不能泛化成普通用户 API 权限 | 边界已澄清：当前仅状态与断开两条路由接受设备 token，且无 6c API；进入 6c 设计前需再次复核新增路由为零或逐单元显式授权，不能把当前边界澄清当成未来 API 的授权依据 |

处置方式只有两种：工程修复并通过相应回归；或用户明确接受风险并记录。架构文档、路由矩阵或代码评审本身不能替代回归证据，也不能替代进入 6c 设计的用户确认。

## 12. 发布前收口

v0.1 本地侧收口必须同时满足：

1. Agent、能力资产、简历管理、面试管理、Skill Runtime、Stage 6a / 6b 均有用户模块结论。
2. 简历 RE-05、RE-06、RE-07 已由真实用户完成。
3. 面试状态确认和节点排序已由真实用户完成。
4. 所有 S0 已修复并重验；S1 已修复或由用户明确接受为需修改遗留。
5. 后端依赖缺失导致的 A2 或设备绑定阻断已被如实记录，未被替代通过。
6. `PROJECT_STATE.md` 与统一验收包的结论一致。
7. 验收文档变更已提交并推送 `origin/main`。

Stage 6c 额外满足：

1. Stage 6b 用户本地侧验收为通过。
2. BA-01、BA-02、BA-03 已工程修复并通过回归，或用户明确接受风险。
3. 用户明确同意进入 6c 设计。

任一条件缺失时，不启动授权 API、数据库、云端投影、上传重试或自动导入。
